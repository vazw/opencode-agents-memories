## The five gaps

### 1. Encryption disabled is a no-op — `tests/turso-encryption-migrator.test.ts:124`

Upstream calls `runDatabaseEncryptionMigration()` with encryption disabled and asserts the
`.tursodb-encrypted-v1` marker does **not** appear.

**Port seam:** `run_database_encryption_migration` (`crates/mem-store/src/encryption_migrator.rs`),
driven with a `StoreConfig` whose `database_encryption_enabled = false`; the early return is
`resolve_database_encryption` returning `None` (`:428-431`). The test asserts no marker is written and
the plaintext shard is untouched.

**Mutant:** delete the `None` early return — the conversion runs and/or the marker appears.

### 2. `ShardManager` usable after `metadata.db` encryption — `tests/turso-encryption-migrator.test.ts:210`

Upstream warms the shard manager, migrates `metadata.db` to encryption, and asserts the manager still
lists the shards.

**Port seam:** after `run_database_encryption_migration`, call `ShardManager::get_all_shards`
(`crates/mem-store/src/shard_manager.rs:516`) and assert the known shard is returned. The CONFIG flip has
no port analog: `StoreConfig` is snapshotted into `ConnectionManager` at construction
(`crates/mem-store/src/connection.rs:97-114`), and a plaintext `metadata.db` does not open with encryption
options, so no manager can be warm on it before the flip. The fixture models the production sequence
instead: the encryption-off run writes `metadata.db` plus one shard and drops every handle; the
encryption-on run over the same root migrates and reads.

**Mutant:** a migration that leaves `metadata.db` unconverted or half-swapped, so the encryption-on manager
cannot open the active path and `get_all_shards` fails. The upstream "re-keys it while a warm handle is
still cached" variant is unreachable in this port for the reason above; `reset()` and the `ptr_eq`
revalidation are covered structurally, not by this case.

### 3. Reopen after `closeConnection(skills.db)` without a lifecycle reset — `tests/skills-manager.test.ts:149`

Upstream closes the shared `skills.db` connection directly and asserts the next `list()` reopens; it
does **not** call the lifecycle reset. The port's `reopens_after_reset`
(`crates/mem-skills/tests/skills_manager.rs`) covers only `SkillsManager::reset()`, which clears the
cached `OnceCell<DbHandle>`.

**Port seam:** the cached `skills.db` handle must be closed without `reset()`, then
`SkillsManager::list` must reopen and return the existing skills. `ConnectionManager::close_connection`
exists (`crates/mem-store/src/connection.rs:259`), but `SkillsManager` owns its `ConnectionManager`
privately, so the implementation either exposes a narrow close/reopen accessor delegating to it or adds
the equivalent test seam. Do not route the test through `reset()` — that is the already-covered path.

**Mutant:** a cached handle that is never re-opened after the raw close (stale connection error).

### 4. A 501-row import is one atomic transaction — `tests/memory-portability.test.ts:205`

Upstream imports a 501-memory bundle and asserts the import is a single atomic transaction.

**Port seam:** `PortabilityService::import` (`crates/mem-portability/src/service.rs:388`) over a
501-memory bundle; assert every row lands, and that a fault injected mid-import leaves **zero** rows —
the atomicity claim, not just the count.

**Mutant:** per-row autocommit (or a commit before the loop ends) — the fault leaves a partial target.

### 5. Host-side step-capped agent registration — `tests/plugin-host-config.test.ts:177`

Upstream's `applyStructuredOutputAgentConfig` registers `STRUCTURED_OUTPUT_AGENT` on the host config
object with `description`, `mode: "subagent"`, `steps`/`maxSteps: STRUCTURED_OUTPUT_MAX_STEPS`,
`tools: STRUCTURED_OUTPUT_TOOLS`, `permission: { "*": "deny", StructuredOutput: "allow" }` and
`options.thinking: { type: "disabled" }`. The port only sends `agent: opencode-mem-structured` in the
request body (`crates/mem-ai/src/provider/opencode_host.rs:308`); the wrapper registers no `config`
hook (`plugin/src/plugin.js:709`) and has no `STRUCTURED_OUTPUT_TOOLS`.

**Port seam:** the wrapper's host-hook surface — add the `config` hook (or extend the adapter's
equivalent), then drive it with a config object and assert the `STRUCTURED_OUTPUT_AGENT` entry
field-for-field. The step cap itself already exists in the provider's loop
(`max_steps` in `crates/mem-ai/src/provider/opencode_host.rs`); what is unported is the registration.

**Mutant:** a registration without `tools`/`permission` (the least-privilege claim) or without the
`thinking: disabled` option.
