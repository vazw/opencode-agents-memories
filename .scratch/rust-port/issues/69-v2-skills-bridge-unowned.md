## What is missing

Upstream's `v2-skills-bridge` registers the skills catalogue with the V2 adapter. Issue 26's AC named it as
a behaviour to port and attributed it to issue 20; 20 landed as `56df86a` with four behaviours
(`v2-loader-contract`, `v2-plugin-adapter`, `v2-legacy-client`, `tui-companion`) and only recorded that
"this lane only unblocks its bridge half". No lane owns the bridge itself.

**Measured at `8023dd8`:** `grep -rn skills plugin/src/v2/*.js plugin/index.js` → nothing. The Rust side is
complete: `/api/skills`, `/api/skills/{id}` and both catalogue paths are live
(`crates/mem-web/src/api/mod.rs:295`–`:339`, handlers in `crates/mem-web/src/api/skills.rs`).

## The open design question — do not plan until it is ruled

Where does the bridge live? Two candidates:

- **A — plugin-side catalogue read.** The V2 adapter reads the catalogue over the existing HTTP surface.
  No new wire method; but the plugin would need a base URL and auth it does not have today.
- **B — a `skills` wire method.** The engine answers a catalogue read and the adapter forwards it. Follows
  the existing seam, but `docs/bridge-schema.md` and `tests/fixtures/bridge/**` are frozen, and the method
  list is pinned in `hello-response.json`, so this is not additive by default.

A third possibility — declare the behaviour **N/A** because the host has no skills-consumer surface — is
not excluded, but it needs the same evidence a port would: what the host does with a registered skill.

## Agent Brief

**Category:** enhancement

**Summary:** give the V2 adapter the skills bridge it deliberately excluded, via a `skills` wire method and
`ctx.skill.transform` — guarded by the capability flag issue 68 introduces.

**The ruling.** Owner chose **B**: the engine answers the catalogue over the existing stdio seam and the
adapter registers it with the host. Option A (the plugin reads `/api/skills` over HTTP) was rejected because
it needs a second transport plus a base URL and auth token the plugin does not have; option C (N/A) was
rejected because the host exposes a first-class skill domain and upstream registers through it.

**Current behaviour (verified at `a0d0f66`):**
- `plugin/src/v2/adapter.js:9` explicitly excludes *"any tool and skill registration (issues 22/26 own those
  surfaces)"* — 22 delivered tools, 26 was narrowed, and the skills half lives here.
- The host exposes `ctx.skill: SkillDomain` (`packages/plugin/src/promise/plugin.ts:52`), built into the
  context at `packages/plugin/src/promise/adapter.ts:474`; `SkillEditor { list, get, add, update, remove }` and
  `transform`/`reload` at `packages/plugin/src/promise/skill.ts:7`–`:19`.
- `Skill.Info` is `{ id, name, description?, autoinvoke?, path: AbsolutePath, content }`
  (`packages/schema/src/skill.ts`).
- Upstream's `registerDbSkills` (`example/opencode-mem/src/v2/adapter.ts:60`–`:95`) lists the catalogue, adds
  each skill, and removes stale ids by reconciliation.
- Our catalogue is Rust-side: `skills.db` plus `skills-content/{id}/SKILL.md`, and
  `crate::skill_content_path(storage_path, id)` (`crates/mem-skills/src/content.rs:38`) already returns the
  absolute `SKILL.md` path — exactly the `path` the host requires. The HTTP surface is `/api/skills`
  (`crates/mem-web/src/api/mod.rs:295`–`:339`), which the plugin cannot reach.
- The engine's `hello` advertises five methods (`crates/mem-bridge/src/engine.rs:145`), pinned in
  `tests/fixtures/bridge/hello-response.json`; the wire schema and fixtures are frozen.

**Desired behaviour:**
1. **Engine:** a `skills` method. Request carries the envelope plus the host project (`project_id` = the raw
   `ctx.location.directory`, the same value `inject`/`recall` use); response
   `{ "skills": [{ id, name, description?, autoinvoke?, path, content }] }` with `path` from
   `skill_content_path`. Project-scoped, like upstream's `containerTag` list.
2. **Capability:** the engine advertises `capabilities.skills: true` through issue 68's mechanism, and the
   adapter only calls `skills` when it is present. An older engine no-ops rather than answering a wrong shape.
3. **Adapter:** on `setup`, read the catalogue and `ctx.skill.transform(editor => …)` — add/update each skill,
   remove ids that disappeared, exactly upstream's reconciliation. Re-register on the host's skills-changed
   event if the host emits one (measure; do not assume).
4. **Schema unfreeze:** `docs/bridge-schema.md`, `tests/fixtures/bridge/**` (including the `hello` methods
   list and the new capability), and the engine's `methods` array. This is the cost of B and is ruled.

**Key interfaces:** `SkillService`/the skills store, `skill_content_path`, `Engine`'s dispatch and
`handshake_result`, `plugin/src/v2/plugin.js`'s `setup`, `plugin/src/v2/adapter.js`, `ctx.skill.transform`.

**Acceptance criteria:**
- [ ] An engine test: `skills` returns the catalogue with absolute `path`s and the exact `Skill.Info` field
      set; an unknown project or an empty catalogue is a typed empty list, not an error.
- [ ] A wrapper test over the real `setup(ctx)` with a fake `ctx.skill.transform`: two skills are added with
      the exact payload; a second call with one removed issues `remove(id)` for it and not the survivor.
- [ ] A test with `capabilities.skills` absent: no `skills` request on the wire and no registration.
- [ ] `hello` advertises the capability and the method; the fixture and its schema test move with it.
- [ ] `plugin/dist/v2/**` is the byte-identical twin; `dist-sync` and `bundle-boundary` stay green; no new
      dependency; production panic-free.

**Out of scope:** writing skills from the plugin (registration is read-only); the HTTP `/api/skills` surface;
issue 26's portability transport; issue 67's compaction hook.

**Sequencing:** issue 68 first. Both edit `tests/fixtures/bridge/hello-response.json`, and 69 relies on the
capability flag 68 adds; running them concurrently would rebuild that guard twice.
