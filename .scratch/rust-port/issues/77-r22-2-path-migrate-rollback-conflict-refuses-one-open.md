# 77 — mem-store · R-22-2: a path-migrate rollback that reactivates a conflicting target refuses one open

Status: needs-triage — 2026-10-29 (residual **R-22-2** of `docs/adr/0022-one-active-shard.md`; site `shard_path_migration.rs:217-226`; no in-tree test constructs the state)

> *This was generated by AI during triage.*

## What

ADR-0022 makes a second `is_active = 1` row per `(scope, scope_hash)` a database constraint. Three
`register_existing_shard` call sites change failure mode as a result. This issue owns the one that can
refuse an open: `rollback_archived` registering a restored target.

`rollback_archived` (`crates/mem-store/src/shard_path_migration.rs:192`) restores a target shard that an
interrupted path migration had archived. It passes `archived.is_active` straight through
(`:217-226`, `?`). When that is `true` and the tuple already holds a *different* active row, the upsert
now raises `ActiveShardConflict` — after the file has already been moved back.

## Mechanism (READ, cited by symbol)

The failed step is **not** side-effect-free, and that is the point:

1. `rollback_archived` removes whatever sits at `original_path` (`:204`), then renames
   `archive_path → original_path` (`:212-216`) — **the filesystem rollback is done**.
2. It then registers the restored shard (`:217-226`) with `archived.is_active`. A conflict here returns
   `Err` **after** the rename.
3. `rollback_swap` treats a per-item failure as soft: it warns `"Path migration target rollback failed"`
   and sets `rollback_failed = true` (`:241-253`), so the journal is **not** removed (`:278-285`).
4. `rollback_from_journal` calls `rollback_swap(…).await?` and **discards the `bool`** (`:370`), so it
   returns `Ok(())`.
5. `recover_interrupted_swap` sees an `Ok` outcome but a surviving journal and returns
   `shard_recover_error(&state_path, "rollback could not restore every shard")` (`:317-327`, `:332-340`),
   i.e. literally:
   `Internal { message: "Failed to recover path-migrate swap <storage>/path-migrate-swap.json: rollback could not restore every shard" }`.
6. `ReadyGate::run_steps` propagates with `?` (`ready.rs:114-119`), so `ensure_ready()` fails and the
   store does not become ready.

**Reachability requires an active archived target.** `ArchivedTarget.is_active` is copied from the
target's own pre-existing shard rows (`:774-786`), not invented — so a target that had no active shard
cannot conflict. The conflicting row is typically created by the legacy reconcile, which the ready gate
runs **before** path recovery (`ready.rs:233-256`) and which registers the highest parsed file of a tuple
as active (`legacy_migrator.rs:843-855`).

## Severity — one refused open, not a permanent wedge

After the failed attempt the archive no longer exists at `archive_path` (it was renamed onto
`original_path`). On the next open `rollback_archived` returns `Ok(())` early (`:201-203`), so
`rollback_failed` stays false, the journal is removed, and the gate passes. The registry row for the
restored shard is re-created by the reconcile that runs first on that open.

So the residual costs **one failed start**, not an unopenable store. The reason it still matters: the
engine is spawned once by the plugin, so a failed first start is user-visible as a dead session, and the
error text names a swap file rather than "retry". `ensure_ready()` does clear `in_flight` on failure
(`ready.rs:103-110`), so an in-process retry works.

One caveat, unmeasured: if the rename itself fails midway (archive and original both present), the early
return does not apply and the retry repeats the same conflict.

## The other two sites (for completeness, both improved)

- `shard_path_migration.rs:619` — inventory registration inside `migrate`, `.map_err(PathMigrationError::Store)`
  at `:628`: the **explicit** `migrate` command now aborts with the typed conflict instead of silently
  creating a second active. Fail-closed on a user-invoked command; diagnosable.
- `legacy_migrator.rs:848` — the reconcile site: `ActiveShardConflict` is the one arm that warns and
  continues (D-22-8, `:857-873`); every other registration error still aborts the open (`:875`).

## Why W4 did not fix it

Which row wins is a policy question, not a mechanical one: the restored archive is the pre-swap truth,
while the reconcile row is an artifact of the interrupted state. Deactivating the conflicting row inside
the rollback would mutate the registry outside the journal's own record and needs its own discriminating
test. W4's scope was the invariant, so the site is named as R-22-2 with an inverted world and the trigger
"first operator report".

## How to close

The recovery fixture family already exists (`crates/mem-store/tests/shard_path_migrate.rs:777` runs
`gate.ensure_ready()` over a seeded journal). The missing state is only:

1. an interrupted swap with an **active** archived target, and
2. a different active row in the same `(scope, new_hash)` tuple at recovery time.

Assert both halves and the residual is pinned:

- first `ensure_ready()` → `Err(Internal)` whose message contains
  `Failed to recover path-migrate swap` and `rollback could not restore every shard`;
- second `ensure_ready()` → `Ok`, the journal is gone, and `get_all_shards(new_hash)` holds the restored
  shard with its pre-swap `is_active`.

Then choose the policy: (a) keep the one-failed-open behaviour and make the error text name the retry, or
(b) deactivate the conflicting row inside `rollback_archived` so the recovery completes on the first
attempt. (b) is the semantic fix — a rollback should win — but it needs its own inversion (revert the
deactivation → the first open fails again).

## Falsifier

If a fixture that builds the state above shows the **first** `ensure_ready()` succeeding, R-22-2 is not
reachable in that shape and this issue closes as no-defect. Conversely, an operator reporting
`Failed to recover path-migrate swap … rollback could not restore every shard` is this path firing.
