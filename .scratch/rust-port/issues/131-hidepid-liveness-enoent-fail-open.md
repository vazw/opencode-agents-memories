## Problem

`observe_process` (`crates/mem-store/src/platform.rs:206-211`) accepts `ENOENT` as the only
absence-that-proves-death (`Err(NotFound) => ObservedProcess::Absent`). Under a `hidepid=2`
mount, `/proc/<pid>` of ANOTHER USER's process reports exactly `ENOENT` — the code's own comment
records the indistinguishability ("a `hidepid=` mount reports ENOENT for other users' pids, so
that case is indistinguishable from absence"). READ-verified 2026-11-08 at HEAD: the fail-open is
live — a cross-user lock holder is observed `Absent` ⇒ `Dead` ⇒ lock considered stolen.

Exposure bound: `hidepid=2` keeps *same-uid* processes visible, and every lock path in the stated
threat model (engine lock, operation locks, the `.wal-mode` marker, the W6 sweep) is same-uid;
the audit graded the cross-user variant out of the threat model (REPORT `:59-61`). This is
hardening/correctness of a shared primitive, not a W6 blocker.

## Fix shape (from the draft; the blueprint confirms the seam)

- `observe_process` accepts ENOENT as `Dead` ONLY when corroborated by `kill(pid, 0) == ESRCH`;
  ENOENT + `EPERM`/success (or off-Unix) stays `Alive`. `kill()` does not read `/proc`, so
  hidepid cannot spoof it.
- Home: `mem-store::platform` (downstream of nothing; the `mem-profile`
  `learning_lock.rs:15-16` `/proc`-absent-AND-ESRCH precedent's logic moves DOWN into the shared
  primitive — dependency direction resolves clean; `mem-profile` depends on `mem-store`).
- Platform-matrix tests. The discriminating test must not require a real hidepid mount
  (synthetic `/proc` fixture or injected seam — planner decides); a live hidepid=2 measurement
  via unshare/mount namespace is a best-effort first step, not a gate.
