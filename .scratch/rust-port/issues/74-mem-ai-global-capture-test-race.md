# 74 — `mem-ai`'s provider test binary has a real race on the process-global capture set

Status: done — 2026-10-29 — landed at `99bf621` (merge of `78cbcb2`; three test files, `+32/−0`). The issue's AC #2 is closed by substitution as the blueprint ruled: the barrier reproducer is deleted (it calls `clear()` outside the gate and would fail on a correct fix); the after-side is the structural argument + the exact-binding inventory + `32 passed` at `--test-threads=16` × 100.

## What happened

One `cargo test --workspace` run failed a single test on a tree that touches **zero** files under
`crates/mem-ai`:

```
internal_capture_sessions::test_internal_session_set_global
  assertion failed: grace keeps it visible
```

It passed on the rerun and in every subsequent measurement. The failure is real, not noise: it is a
test-isolation race inside **one** test binary.

## Mechanism (READ, cited by symbol)

`crates/mem-ai/tests/provider.rs` mounts four modules into a single test binary, including
`internal_capture_sessions` and `opencode_provider`. Cargo runs the binary's tests **in parallel
threads by default**, and both modules mutate the same process-global state:

- `InternalCaptureSessions::global()` is the process-wide set (`crates/mem-ai/src/provider/internal_capture.rs`).
- `test_internal_session_set_global` (`tests/provider/internal_capture_sessions.rs:46`) does
  `first.clear(); first.track("ses_global")`, then `second.untrack("ses_global")` — which leaves a
  **grace deadline** — and asserts `first.is_tracked("ses_global")` with the message
  `grace keeps it visible` (`:58`).
- `tests/provider/opencode_provider.rs:166` and `:183` call `guard.clear()`, which wipes the whole
  tracked map (`internal_capture.rs:121-124`).

So a `clear()` from an `opencode_provider` test scheduled between the `untrack` and the assert erases
the grace entry, and the assertion fails. Nothing in the failing path belongs to the branch under
review.

## Evidence (MEASURED, issue 43 W2 review)

## Desired behaviour

The provider test binary's global-state tests do not interfere with each other, so a green workspace
run means what it says. No production behaviour changes.
