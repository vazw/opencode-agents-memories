# 72 — Scope-wide delete-by-id (W1b residual)

Status: ready-for-agent — 2026-10-28 (split from issue 43's triage; small and self-contained)

> *This was generated by AI during triage.*

## What

`delete_memory_by_id` takes a single `Db`. A memory id can exist in **more than one shard** of a scope
(43.1's deterministic-id writers), so deleting by id can leave a copy behind. The retention path (issue 39)
deletes by id and counts by registry, which makes this load-bearing for it.

## Evidence

- `shard_manager.rs` sorts `get_all_shards` by `Reverse(shard_index)`; `inject.rs` dedups accepted memories
  through a `seen: HashSet<String>`. The W1b note at `43:588-594` is partly stale — the highest-index read
  preference and the inject dedup already exist — but **scope-wide delete-by-id is not verified**:
  `delete_memory_by_id` still takes a single `db`.
- The write path's scope scan was measured at 53 µs (k=1) / 131 µs (k=5) / 453 µs (k=20) with cached
  handles (issue 43's re-verification), so a fan-out delete is affordable.

## Acceptance

- [ ] A test seeds the same id in two shards of one scope and deletes it once; both copies are gone and a
      differently-id'd neighbour survives.
- [ ] An unreadable shard is a typed error (`ScopeShardUnreadable`, W1), not a silent skip — the delete must
      not fail open.
- [ ] No new dependency; production panic-free.
